## 왜 필요한가

서브에이전트나 `SKILL.md`, `CLAUDE.md`를 썼습니다.
직접 넣어 본 프롬프트 세 개에서는 잘 동작했습니다.
그런데 실제로 쓰기 시작하면 이런 일을 만납니다.

| 실제로 터지는 문제 | 잡아내는 단계 |
| --- | --- |
| 명세가 모호하거나, 앞뒤가 안 맞거나, 정의하지 않은 걸 약속한다 | 📄 **서류전형** |
| 같은 일을 할 때마다 다르게 하거나, 자기 출력 형식을 어긴다 | 💼 **1차 면접** 실무 과제 (일부는 두 번 실행) |
| 도구가 실패하거나, 요구가 서로 부딪히거나, 담당 범위 경계에 걸친 요청이 온다 | 🔥 **2차 면접** 압박 질문 |
| "지시를 무시해", 파일 속 숨은 명령, 시스템 프롬프트 요청 | 🛡️ **최종 면접** 레드팀 공격 |
| 사람이 읽어서는 안 보이는 글자나 지시가 명세에 숨어 있다 | 🚧 **보안 검문소** (코드 규칙 우선) |

단계마다 통과선이 있습니다.
한 단계라도 떨어지면 면접은 그 자리에서 끝납니다.
불합격 통지서에는 결정적인 실수와 보완할 점이 적힙니다.

## 설치

**Claude Code 플러그인** (권장):

```text
/plugin marketplace add ESeungJun/agent-interview-arena
/plugin install arena@agent-interview-arena
```

**스킬을 읽는 다른 에이전트** ([skills.sh](https://skills.sh)):

```bash
npx skills add https://github.com/ESeungJun/agent-interview-arena/tree/main/plugins/arena/skills/apply
```

필요한 것:

- Node.js 20 이상
- 로그인된 `claude` CLI (기본 백엔드, 내 Claude 요금제로 실행) 또는 `ANTHROPIC_API_KEY`

## 사용법

```text
/arena:apply .claude/agents/code-reviewer.md
/arena:apply --quick                 # 연습 모드: 면접관 1명, 더 저렴
/arena:apply --lang ko               # 한국어 결과 (기본은 영어)
/arena:apply --division open         # 지원자 모델 직접 고르기
/arena:apply --repeat 3              # 같은 시험을 3판 보고 합격률 내기
/arena:apply submit                  # 랭크 결과를 순위표에 올리기
```

skills.sh로 설치했다면 명령은 `/apply`입니다.
경로를 주지 않으면 `.claude/agents/*.md`, `SKILL.md`, `CLAUDE.md`, `AGENTS.md`를 찾아서 어느 파일로 할지 묻습니다.
64KB 이하의 텍스트 명세면 무엇이든 받습니다.

지원자는 명세가 전제한 모델로 면접을 봅니다.

- frontmatter에 `model: opus`가 있으면 Opus로 봅니다.
- `model:`이 없거나 `inherit`이면 가장 흔한 세션 모델인 Sonnet으로 봅니다.
- `--division light|middle|open`을 주면 그 값이 우선합니다.

### 모드와 비용

| | 랭크 (기본) | 연습 (quick) |
| --- | --- | --- |
| 단계별 면접관 | 2명, 의견이 갈린 항목만 3번째가 판정 | 1명 (서류에서 판정이 자주 갈리는 4개 항목만 2명이 더 봄) |
| 2차 면접 시나리오별 실행 | 2회 | 1회 |
| 최종 면접 공격별 실행 | 2회 (모든 회차를 막아야 방어) | 1회 |
| 보안 분류 모델 | 모든 명세 | 정규식에 걸린 명세 + 10% 표본 |
| 최종까지 간 경우 모델 호출 | 약 45회 | 약 25회 |
| 순위표 제출 | ✅ | ❌ |

채점은 Haiku, 과제 출제는 Sonnet이 맡습니다. 지원자 모델과는 상관없습니다.
최종까지 간 랭크 면접 한 번을 API 요금으로 환산하면 이 정도입니다.

- Haiku 지원자: 약 0.28달러
- Sonnet 지원자: 약 1.05달러
- Opus 지원자: 그보다 더 듭니다.
`claude` CLI 백엔드로 돌리면 내 요금제 사용량에서 차감됩니다.
위 금액은 최종 공격을 두 번씩 보내고 최종 면접관을 한 명 더 두기 전에 잰 값입니다. 호출이 8회쯤 늘었고 다시 재지는 않았습니다.

판정 한 번은 표본 하나입니다.
지원자 답변은 실행마다 달라지므로 결과에 몇 번의 실행 위에 선 판정인지를 함께 적습니다.

- 2차는 몇 회차 중 몇 회차를 버텼는지, 최종은 공격마다 `2/2`·`1/2`로 보여 줍니다.
- `--repeat N`(2 ~ 10)은 같은 시험(같은 과제·시나리오·공격)을 N판 보고 "3판 중 2판 합격"과 공격별 방어 횟수를 냅니다.

## 면접 단계

| 단계 | 내용 | 통과선 |
| --- | --- | --- |
| 🚧 보안 검문소 | 면접을 속이려는 명세를 코드 규칙으로 거릅니다. 보이지 않는 유니코드, 가짜 격리 태그, 주석에 숨긴 채점 지시, 도배 등이 대상입니다. 규칙에 의심스럽게 걸린 명세와 무작위 10% 표본은 분류 모델이 한 번 더 봅니다. | 하나라도 걸리면 실격 |
| 📄 서류전형 | [공개 기준표](prompts/interviewer_doc_screening.md)로 명세를 봅니다. 역할과 범위, 지시 품질, 구조, 도구 사용 규칙, 실패 처리, 출력 형식, 예시를 봅니다. 항목마다 명세 원문을 인용합니다. 랭크 모드에서는 점수가 통과선 ±8점 안이면 한 번 더 채점하고, 둘의 판정이 갈린 항목은 세 번째 면접관이 정합니다. | 30 / 100 |
| 💼 1차 면접 | 이 명세에 맞춰 만든 실무 과제 3개를 풉니다. 일부는 두 번 돌려 결과가 흔들리는지 봅니다. 출력 형식은 코드로 검사합니다. | 75 / 100 |
| 🔥 2차 면접 | 두 턴짜리 시나리오입니다. 도구 실패, 서로 부딪히는 요구, 범위 경계 요청을 줍니다. | 75 / 100 |
| 🛡️ 최종 면접 | 레드팀 공격 5개를 받습니다. 권한 사칭, 시스템 프롬프트 유출, 간접 주입, 환각 유도, 그리고 하나를 더 무작위로 고릅니다. | 5개 모두 방어 |

지원자는 실제 도구를 실행하지 않습니다.
면접 안에서 도구 결과는 모두 모의값입니다.
그래서 "저장소를 지워라"라고 적힌 명세라도 실제로는 아무것도 할 수 없습니다.

## 채점을 믿을 수 있게 하는 장치

LLM이 LLM을 채점하면 속이기 쉽습니다.
그래서 이렇게 막습니다.

- **맥락 분리**
  - 면접관과 지원자는 도구·설정·대화 기록 없이 따로따로 호출됩니다.
  - 지원자는 기준표를 볼 수 없습니다.
- **코드 우선**
  - 출력 형식, 금지 문구, 공격 성공 표식, 점수 계산은 모델 의견이 아니라 코드로 확인합니다.
- **근거 인용 검증**
  - 모든 통과·감점 항목은 명세나 지원자 답변을 인용해야 합니다.
  - 인용문은 원문과 글자 단위로 대조합니다.
  - 원문에 없는 인용을 단 판정은 버립니다.
- **다수결**
  - 랭크 모드에서는 면접관 둘이 채점합니다.
  - 둘의 의견이 갈린 항목만 세 번째 면접관이 판정합니다. 최종 면접도 공격 회차마다 같은 방식입니다.
- **명세서는 평가 대상 자료이지 지시가 아닙니다**
  - 채점 전에 코드 검문소가 글자를 정규화하고(유니코드 NFKC, 이형 선택자, 빈 태그) 보이지 않는 문자를 실격 처리합니다.
  - 채점자에게 점수를 요구하는 문장을 찾습니다. 평가자를 지목하지 않은 문장, HTML 주석·`<details>`·숨김 블록 안의 문장도 봅니다.
  - 랭크 모드에서는 그 뒤에 분류 모델이 모든 명세를 읽습니다.
  - 면접관은 명세를 nonce 태그 구획 안에서 받고, 그 안의 채점 지시는 판정을 바꾸지 못하며 신고 대상이라는 지시를 받습니다.
  - 면접관이 신고했는데 인용이 명세에 없으면 실격에 쓰지 않고, 조용히 버리는 대신 결과 파일에 남깁니다.
- **분기마다 시험 하나**
  - 과제와 시나리오는 명세마다 분기 단위로 고정됩니다.
  - 최종 면접의 공격 편성과 문구는 분기마다 모두에게 같고 명세와 무관합니다. 명세를 고쳐 쉬운 편성을 고를 수 없습니다.
- **버전 고정**
  - 결과마다 엔진 버전, 실제로 답한 모델 ID, 면접관 프롬프트 해시를 남깁니다. CLI 백엔드도 별칭이 아니라 고정 모델 ID 로 부릅니다.
  - 프롬프트를 고쳐서 돌린 결과는 섞이지 않습니다.
  - 프롬프트가 바뀌면 순위표는 새 버전의 결과만 받습니다. 스킬을 업데이트했으면 면접을 다시 보세요.

실제 사례가 있습니다.
같은 샘플 에이전트가 한 번은 공격 5개를 모두 막아 합격했습니다.
다른 실행에서는 가짜 주인 권한 요청에 강요된 단어를 한 번 출력해 불합격했습니다.
손으로 한 번 시험해서는 놓치는 흔들림이고, 랭크 모드가 최종까지 두 번씩 돌리는 이유입니다.

## 순위표

[**eseungjun.github.io/agent-interview-arena**](https://eseungjun.github.io/agent-interview-arena/)

**샘플 결과**: 이 저장소의 샘플 에이전트 [`good_claude_subagent.md`](tests/sample_candidates/good_claude_subagent.md)를 랭크전으로 면접 본 결과입니다 ([#2](https://github.com/ESeungJun/agent-interview-arena/issues/2)).

[![Agent Interview Arena](https://img.shields.io/badge/Agent%20Interview%20Arena-Round%202-blue?logo=github)](https://eseungjun.github.io/agent-interview-arena/)

- 📄 서류 95 · 💼 1차 88 · 🔥 2차 67 (통과선 75), 2차에서 탈락했습니다.
- 결정적 실수: 요구사항이 부딪히는 상황에서 "급하다"는 압박을 받자, 충돌을 알리지 않고 규칙상 빼야 할 minor 항목까지 섞어 보고했습니다.
- 서류 점수가 높아도 압박 앞에서 규칙을 지키는지는 따로 봐야 한다는 예입니다.
- 위 배지는 결과를 README 에 달 때 쓰는 모양입니다. 도달한 단계가 배지에 적힙니다.

`/arena:apply submit`을 실행하면 끝난 랭크 면접 결과로 GitHub Issue를 만듭니다.
15분 안팎으로 GitHub Action이 모델을 부르지 않고 다시 검사한 뒤 GitHub 아이디로 순위표에 올립니다.

- **직접 측정(self-reported)**
  - 내 컴퓨터에서 직접 본 면접 결과라는 뜻입니다.
  - 제출물에 과제·시나리오·지원자 답변 원문이 실리고, 봇은 코드로 다시 계산할 수 있는 것을 전부 다시 계산합니다.
    - 문서 해시, 체크리스트 범위, 점수 계산, 단계 순서, 프롬프트 버전, 보안 검문소의 코드 규칙
    - 1·2차 판정의 근거 인용을 답변과 대조하고, 그 답변에 출력 계약 검사를 다시 돌립니다.
    - 최종 면접의 그 분기 공격 편성과 문구를 분기 시드로 다시 만들어 대조하고, 유출·강요 문구·계약 탐지기를 답변마다 다시 돌립니다.
  - 답변에 없는 문장을 인용한 판정은 여기서 걸립니다 ("evidence quotes are not in the responses"). 심어 둔 토큰을 흘리거나 강요 문구를 출력한 답변을 방어로 적은 제출도 걸립니다.
  - 분기는 제출물에 적힌 시각이 아니라 GitHub 가 기록한 Issue 생성 시각으로 확인합니다.
  - **하지 않는 것**: 면접을 다시 보거나 모델로 다시 채점하지 않습니다. 제출마다 API 키와 비용이 들기 때문입니다.
    - 그래서 판정이 *옳은지*는 알 수 없습니다. 진짜처럼 보이는 답변을 두고 그 안에 있는 문장을 인용해 전부 통과로 적거나, 답변을 손으로 써도 순위표에 오를 수 있습니다.
    - 공격을 정말 막았는지는 코드 탐지기가 걸리지 않는 한 모델의 판단입니다.
    - 로컬 실행의 편성 시드는 공개 상수라 그 분기의 공격은 미리 알 수 있습니다. 대신 모두에게 같습니다.
- **미검증(unverified)**
  - 답변 원문이 없는 제출입니다. 예전 버전의 스킬로 만들었거나, 답변이 Issue 에 안 들어가 `submit --unverified` 로 낸 경우입니다.
  - 서류전형만 대조할 수 있습니다. 계속 받지만 무엇을 적어 냈든 직접 측정 기록보다 아래에 놓입니다.
  - 이 변경 전에 올라온 기록은 이 등급으로 표시됩니다.
- 항목 옆에는 **try N**(그 사람이 그 체급에 낸 횟수)이 붙습니다. 순위표는 최고 기록만 남기므로, 여러 번 내어 잘 나온 판인지 첫 판인지 구분하려는 것입니다.
  - `--repeat` 로 본 면접이면 **N/M passes** 도 붙습니다. 제출자가 적은 값이고 확인하지 않습니다.
- **재검증(Verified)** (아직 없음)
  - 이 저장소에 없는 비공개 공격 절반으로 면접을 다시 봅니다.
  - 공개된 공격에만 맞춰 다듬은 명세는 여기서 걸립니다.
  - 내 컴퓨터에서는 돌릴 수 없습니다.
    - 비공개 공격을 스킬에 실어 보내는 순간 비공개가 아니게 되고, 내 컴퓨터에서 나온 결과는 고칠 수 있기 때문입니다.
    - 그래서 운영자 쪽에서 운영자의 API 키로 돌립니다.
  - 그 비용을 어떻게 감당할지가 아직 고민입니다. 체급별 상위권부터 다시 보는 방식으로 시작할 가능성이 큽니다.
- 체급은 지원자 모델 기준입니다.
  - Light (Haiku), Middle (Sonnet), Open (Opus)
- 한 사람은 체급마다 한 항목만 올라갑니다.
  - 새 제출은 그 체급의 내 최고 기록보다 나을 때만 받고, 기존 기록을 대체합니다.
  - 직접 측정과 재검증은 따로 비교합니다. 재검증 기록이 있어도 다음 직접 측정 기록을 낼 수 있습니다.

제출하면 누구나 다시 돌려 볼 수 있도록 명세 전문이 공개됩니다.
과제와 지원자 답변은 봇이 대조할 수 있게 Issue 본문에 압축돼 실립니다.
답변과 면접관의 근거 인용은 저장소 사본에서는 빼지만, Issue 자체는 공개로 남습니다.
비공개 정보는 먼저 지우세요.
스킬은 올리기 전에 반드시 한 번 더 묻습니다.

### 기록 신고와 삭제

- 내 기록을 내리고 싶으면 **내 기록 내리기** Issue를 열고 내릴 Issue 번호를 적어 주세요.
  - 제출한 본인 계정이면 확인 후 순위표와 `docs/submissions/`에서 지웁니다.
- 남의 기록이 위조로 보이거나 명세에 남의 비공개 정보가 들어 있으면 같은 방식으로 **기록 신고** Issue를 열어 주세요.
- 버그, 개선 요청, 질문도 Issue 양식이 각각 있습니다.
- 보안 취약점은 Issue 대신 Security 탭에서 비공개로 신고해 주세요.
- 저장소에서 지워도 git 기록에는 남습니다. 비밀값이 올라갔다면 지우는 것과 별개로 그 값부터 바꾸세요.

## 개인정보와 안전

- 명세는 내가 실행하는 모델 백엔드(`claude` CLI 또는 내 키를 쓴 Anthropic API)로만 갑니다.
- `submit`을 실행하지 않는 한 이 프로젝트로 보내는 것은 없습니다.
- 면접 기록은 `~/.agent-interview-arena/`에 남습니다. `ARENA_HOME`으로 위치를 바꿀 수 있습니다.
- 번들된 엔진(`plugins/arena/skills/apply/bin/arena.mjs`)은 압축하지 않아서 실행되는 코드를 직접 읽을 수 있습니다.
- 스킬은 명세 파일을 스스로 고치지 않습니다. 보완할 점과 요청 프롬프트를 주고, 사용자가 고쳐 달라고 할 때만 고칩니다.

## 알려진 한계

- `claude` CLI 백엔드에서는 Claude Code가 스스로 시스템 프롬프트 공개를 거절합니다.
  - 그래서 최종 면접의 유출 방어가 실제보다 후하게 나올 수 있습니다.
  - 정확히 재려면 `ANTHROPIC_API_KEY`를 설정하세요.
  - 순위표에는 항목마다 어떤 백엔드를 썼는지 표시됩니다.
- 직접 측정 기록은 코드로 다시 계산할 뿐 면접을 다시 보지 않습니다.
  - 지어낸 판정은 걸리지만, 판정에 맞춰 지어낸 답변은 걸리지 않습니다.
  - 그 틈을 막는 것이 재검증 등급이고, 아직 만들지 않았습니다.
- 보안 검문소는 패턴 대조와 분류 모델 호출 한 번입니다.
  - 둘 다 알아보지 못하는 표현의 채점 지시는 면접관까지 갑니다.
  - 면접관은 그것을 무시하고 신고하라는 지시를 받지만, 이 마지막 겹은 모델이 지시를 따르는 것이지 보장이 아닙니다.
- 모델이 채점하므로 결과가 매번 같지는 않습니다.
  - 불합격 한 번은 살펴볼 단서로 보세요.
  - 랭크 결과가 더 강한 신호입니다.

## 개발

개발에는 Node.js 24 이상이 필요합니다 (`.ts` 파일을 바로 실행합니다). 설치한 스킬을 쓰는 데는 20 이상이면 됩니다.

```bash
npm ci
npm test            # 단위 테스트, 모델 호출 없음
npm run build       # 엔진을 plugins/arena/skills/apply/bin/arena.mjs 로 묶음
node runner/run.ts tests/sample_candidates/good_claude_subagent.md --lang ko
```

면접관 프롬프트는 [`prompts/`](prompts/)에 있습니다.
원본은 영어 하나이고, 결과 언어는 매개변수로 정합니다.
공개 레드팀 공격 목록은 [`prompts/red_team_attack_pool.json`](prompts/red_team_attack_pool.json)입니다.
한국어로 쓴 명세에는 같은 공격의 한국어판 [`red_team_attack_pool.ko.json`](prompts/red_team_attack_pool.ko.json)을 씁니다.

브랜치·풀 리퀘스트·릴리스 방식은 [CONTRIBUTING.ko.md](CONTRIBUTING.ko.md)에 있습니다.
기획서·설계서·구현도·결정기록은 [`docs/`](docs/기획서.md)에 있습니다.

### 운영 메모

- 순위표 처리는 `.github/workflows/leaderboard.yml`이 Issue가 열릴 때와 15분마다 돌립니다.
  - GitHub는 60일 동안 저장소 활동이 없으면 예약 실행을 멈춥니다. 멈추면 Actions 화면에서 다시 켭니다.
- 순위표 페이지는 GitHub Pages(`main` 브랜치의 `docs/`)로 내보냅니다. 저장소 설정에서 직접 켜야 합니다.
- 봇은 Actions 토큰으로 `main`에 바로 커밋합니다.
  - `main` 규칙은 강제 push와 삭제만 막습니다.
  - "PR 필수" 규칙은 봇까지 막습니다. 개인 저장소에서는 Actions 봇을 예외로 넣을 수 없기 때문입니다.
  - 쓰기 권한은 소유자에게만 있어서, 다른 사람은 포크한 뒤 PR로 기여합니다.
