# 🥊 엔진 체급 제도 (Engine Divisions)

## 왜 엔진을 하나로 고정하지 않는가

초안은 지원자 전원을 같은 경량 엔진(Haiku/Flash)에 올려 "순수 프롬프트 설계력"만 겨루게 했다. 공정하고 싸지만, **프롬프트는 엔진과 짝을 이뤄야 의미가 있다**는 점에서 검증이 틀어진다.

| 문제 | 설명 |
|---|---|
| 고도(altitude) 역전 | 고성능 모델용 프롬프트는 판단 기준만 주고 세부는 모델에 맡긴다(P-04 권장). 경량 엔진에선 이런 프롬프트가 무너지고, 규칙을 잔뜩 박은 경직된 프롬프트가 이긴다. 정론이 권장하는 설계를 실행 단계가 벌하는 모순 |
| 추론 모델 무력화 | o-시리즈·extended thinking용 프롬프트는 CoT 지시를 일부러 뺀다(M-O2). 비추론 엔진에선 그냥 "생각을 덜 시키는" 프롬프트가 된다 |
| 제조사 불일치 | Gemini용 Few-shot 설계, Claude용 XML 설계를 다른 회사 모델에서 돌리면 서류의 전공 가산(M-xx)과 실행 결과가 따로 논다 |
| 현실과 괴리 | 실제로 그 에이전트가 돌아갈 엔진이 아닌 곳에서 받은 합격증은 실무 투입 근거가 되지 못한다 |

## 결정: 타겟 엔진에서 면접 + 체급별 리그

1. 지원자는 제출 시 **체급과 엔진**을 고른다. 에이전트는 그 엔진에서 그대로 면접을 본다. 추론 강도(reasoning effort / thinking budget)도 체급 한도 안에서 지원자가 설정하는 에이전트 구성의 일부다.
2. 리더보드·명예의 전당은 **체급별**로 나눈다. 같은 체급 안에서는 엔진 배지를 붙이고 제조사별 필터를 제공한다.
3. 체급 안의 엔진은 **정확한 모델 스냅샷 ID로 고정**한다. 제조사가 모델을 교체·폐기하면 **시즌을 리셋**한다(이전 시즌 기록은 아카이브).

| 체급 | 엔진 예시 (시즌마다 스냅샷 고정) | 비용 부담 | 비고 |
|---|---|---|---|
| 🪶 경량급 | Claude Haiku / Gemini Flash / GPT mini | 무료 티켓 | 입문·대량 참가 |
| 🥋 중량급 | Claude Sonnet / Gemini Pro / GPT 표준·추론 | 유료 티켓 | 추론 강도 상한 지정 |
| 👑 무제한급 | Claude Opus / 각사 최상위 | **BYOK**(지원자 API 키) | 키는 면접 동안만 메모리에 보관, 저장·로그 금지 |

## 바뀌지 않는 것

- **서류전형은 체급 공통.** 정적 분석이라 엔진을 쓰지 않는다. 다만 이제 타겟 모델 = 실행 엔진이므로 전공 가산(M-xx)이 실제 실행과 일치한다.
- **면접관은 체급과 무관하게 고정.** 채점 기준이 흔들리지 않게 면접관 모델은 시즌 내내 고정한다.
- **루브릭과 통과선은 체급 공통.** 강한 엔진이 더 잘하는 건 자연스럽다. 그래서 리그를 나눈다.
- 깔때기 구조 유지: 비싼 엔진 호출은 서류를 통과한 지원자에게만 발생한다.

## 새로 생기는 위험과 대응

| 위험 | 대응 |
|---|---|
| 자기 선호 편향: 면접관(예: Claude)이 같은 회사 엔진의 답변을 후하게 봄 | 점수는 코드 계산 + 근거 인용 검증으로 LLM 재량 최소화. 통과선 경계 재채점은 **다른 제조사 모델**로 교차 채점. 시즌 데이터로 제조사별 합격률 편차를 모니터링 |
| 엔진 간 응답 형식 차이 (도구 호출 포맷 등) | 엔진 어댑터 계층에서 공통 메시지/도구 포맷으로 정규화. 도구는 어차피 시뮬레이터 |
| BYOK 키 유출 | 서버 메모리에만, 면접 종료 즉시 폐기. 로그·에러 리포트에 키 마스킹. 지원자 `.md` 실행 환경과 키 처리 환경 분리 |
| 무작위성 차이 (엔진별 temperature 기본값) | 지원자 엔진은 **제조사 기본값**으로 돌린다(실제 운영 조건). 대신 1차 pass^2로 흔들림을 측정 |

## 선택 확장: 이식성 배지 (나중에)

1차 합격자 중 원하는 지원자에 한해 대표 과제(T1)를 다른 제조사 같은 체급 엔진에서도 돌려 "🔁 이식성" 배지를 준다. 합불과 무관한 보너스.
